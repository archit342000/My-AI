## Description
Open items left by the merged batch 5 PRs (#67 to #71), found in review and verification.

1. **PDF page numbers.** Since the RAG text fix, PDF chunks get `page_number` metadata, but when a page's text has only single newlines (what PDF extraction yields) the chunkers report line 1 for every chunk, so later pages' chunks get `page_number` 1. With blank-line paragraph breaks the numbers resolve per page. Fix idea: map chunks to pages by their position in the text, not by line number.
2. **Existing RAG chunks.** Files indexed before the fix keep JSON chunks (and PDFs have no `page_number`). There is no reindex path (`_process_file_background` skips files that already have `content_text`). Fix idea: a one-off script (read `content_text`, `FileRAG.delete_file`, `store_file`).
3. **Short-content gate.** The 50-character gate in `FileRAG.store_file` and its callers in `backend/files/manager.py` measure the stored JSON wrapper, not the text that is indexed, so a very short text file passes. Pre-existing.
4. **Legacy edit and copy.** The legacy UI's edit textarea and copy action still contain the "[System Note: ...]" block (they read the stored content). Fix idea: strip the note for those two paths only; `backend/chat/message_edit.py` re-appends the stored note when the edited text lacks it.

## Acceptance criteria
- [ ] Chunks of later PDF pages carry the right `page_number` even when page text has no blank lines
- [ ] A documented or scripted way to reindex files indexed before the JSON fix
- [ ] The short-content gate measures the text that is indexed (or is recorded as intended)
- [ ] The legacy edit textarea and copy do not include the System Note, stored content unchanged

## Plan

**Date:** 2026-11-20  **Status:** Validated

### Approach
- Pages: for page-based content detected as `document`, `mixed` or `unknown` (the types that go to the paragraph chunkers), chunk each page on its own and stamp that page's number on its chunks, instead of mapping line numbers back to pages. A new `split_pages(clean_text, page_map)` in `chunking.py` returns `(page, text)` pairs; `store_file` runs the chosen chunker per page and numbers chunks sequentially across pages, so no such chunk spans two pages. Page-based content detected as `spreadsheet` or `code` keeps today's whole-text chunking (the spreadsheet chunker takes its header from the first line, which per-page input would break). Rejected: fixing line tracking in every chunker (four chunkers, sub-chunk line accounting, larger change).
- Gate: `store_file` keeps its cheap first checks (not initialised, empty, raw length under `FILE_RAG_MIN_CONTENT_CHARS`, so short malformed content is still skipped without parsing; the hard-coded 50 is replaced by the setting) and then also returns `[]` when the clean text after `content_to_index_text` and `strip_page_markers` has `len(clean_text.strip()) < config.FILE_RAG_MIN_CONTENT_CHARS` (new in `backend/config.py`, default 50; a text of exactly 50 characters is indexed, as `< 50` does today). The manager's three call sites keep `not is_media` and drop only their own `> 50` length check, leaving the length decision to `store_file`, which logs each gate skip once, for the raw and the clean check alike (`log_event("file_rag_skipped_short", {"file_id", "chat_id"})`), for every caller; the manager adds no second event. PDF extraction gates (`PDF_EXTRACTION_MIN_CONTENT`, `pdf_extractor.py`) decide OCR fallback, not indexing, and stay.
- Re-index (redesigned twice: anything that relied on `RAGStore.store`, which swallows embedding and upsert failures, could not tell a real replacement from a partial one): embed first, then write, then prune. `store_file`'s chunk building moves into `FileRAG.build_chunks(file_id, chat_id, content_text, filename=None, timestamp=None, file_type_override=None) -> (documents, metadatas, ids)` (it always parses the stored payload first, so a malformed payload raises `ValueError` whatever its length, then applies the clean-text gate, page handling and ids; `store_file` keeps its raw-length pre-check and its skip log before calling it, so the upload path behaves as before; `store_file` is the only emitter of `file_rag_skipped_short`, and `build_chunks` and `reindex_file` do not log a skip). A new `async FileRAG.reindex_file(file_id, chat_id, content_text, filename) -> str` returns `"reindexed"`, `"skipped"` or `"failed"`: it first reads the file's old ids (`ids_where`; a failure returns `"failed"` with stage `snapshot` and touches nothing), then builds the chunks (a `ValueError` returns `"failed"` with stage `build` and touches nothing, whatever the payload's length); with none (below the gate) it deletes the file's old snapshot ids itself (as in the prune below) and returns `"skipped"`, or `"failed"` (stage `prune`) when that delete raises; otherwise it awaits `rag_manager.embed_texts(documents, task="document")` and returns `"failed"` before writing anything if that raises or returns a different number of vectors than documents; the new chunks get fresh ids for this run (`<file_id>_r<run>_chunk_<i>`, `<run>` a millisecond timestamp), so the writes never merge into old rows or their metadata; it writes them to `vector_collection` (with the embeddings) and `bm25_collection` in batches of `config.CHROMA_UPSERT_BATCH_SIZE` (a new setting in `backend/config.py`, default 100, the value `RAGStore.store` falls back to today through `getattr`); if any write raises, it deletes every new id attempted in this run from both collections (safe because the ids are per-run) and returns `"failed"` (if that rollback delete also fails, it logs stage `rollback` with `write_error` and `rollback_error`, each through `error_detail`, and returns `"failed"` with the old set plus a partial new set, which a rerun replaces); otherwise it deletes the file's older ids from both collections and returns `"reindexed"`. The older ids are read once before any write (`ids_where`), and only the union of that snapshot is deleted; when a snapshot is empty its delete is skipped (Chroma rejects an empty id list). The reads, writes and deletes go through three new `RAGStore` methods that raise instead of swallowing (`ids_where(where)` returning `{"vector": [...], "bm25": [...]}`, the matching ids per collection, `write_batches(documents, metadatas, ids, embeddings)` in batches of `CHROMA_UPSERT_BATCH_SIZE`, and `delete_ids(ids)`, which deletes those ids from both collections and skips an empty list); they are synchronous Chroma calls made from the CLI-only `reindex_file`, so blocking there is accepted (no event loop serves requests in that process), next to `store` and `cleanup` (the collections stay owned by the store `RAGManager` creates, as `docs/data.md` requires); `reindex_file` does not use `delete_file`, whose `cleanup` swallows exceptions. A `build_chunks` error (an invalid stored payload) returns `"failed"` with stage `build`; a failing snapshot read returns `"failed"` with stage `snapshot` before any write; the CLI logs any other exception as `file_reindex_error` with stage `unexpected`. A failed delete after the writes is logged (stage `prune`) and returns `"failed"` with the new set in place and some old rows left, which a rerun removes.  Every `"failed"` branch first logs `log_event("file_reindex_error", {"file_id", "stage": "build" | "snapshot" | "embed" | "write" | "rollback" | "prune", "error": error_detail(e) or a fixed reason for a vector-count mismatch})`, so no failure is silent (the `rollback` event is the one exception to the single `error` key: it carries `write_error` and `rollback_error`). The `reindexed` and `skipped` results log `file_reindexed` / `file_reindex_skipped` with the file id and chunk counts, since they change the index. Invariant: the file's old chunks stay in place until the full new set is in both collections, and a failed run leaves the old set intact, except in two logged cases: a failed rollback (old set plus a partial new set) and a failed prune (full new set plus some old rows); a rerun repairs both. The CLI `python -m backend.files.cli reindex [--file-id ID]` lists files with `db.get_indexable_files(file_id=None)` (`id, chat_id, original_filename, mime_type, content_text`), skips media (their `content_text` is a placeholder, as the upload path's `is_media` check assumes), runs `reindex_file` for each with `asyncio.run`, catches any exception per file (a deliberate per-file boundary against the "avoid bare `Exception`" rule: one bad file must not stop the run; the exception is logged with stage `unexpected`, counted and not hidden) and logs it with `log_event("file_reindex_error", {"file_id", "stage": "unexpected", "error": error_detail(e)})` as a failure, prints only the three counts to stdout, or a fixed message without an id for a `--file-id` that is unknown or has no stored text ("No indexable file with that id.", exit 1, the id logged) or disabled RAG (exit 2) (failure details, with file ids, go to the `file_reindex_error` log events only) (owner decision 1: operator CLIs under `backend/*/cli.py` may print), and exits 1 when any file failed or a given `--file-id` is not found. It is an operator command for an app that is not running: the documented procedure stops the app, runs the command in a one-off container (`docker compose -f docker/docker-compose.yml run --rm app ...`) and starts the app again; nothing in the code enforces that. Re-indexing all files also gives old PDFs page numbers. New public functions get type hints and docstrings (`docs/standards/python.md`).
- Legacy (redesigned after two rounds: a note kept in UI state outlived the edit): a shared `splitSystemNote(text)` helper (moved out of `createMessageBubble`, exposed as `window.MessageManager.splitSystemNote`) returns `{text, note, files}` (`files` is the list it parses today for the attachment pills, `noteFiles`), removing every note block (an edit that adds files makes the router append a second one) and returning them joined as `note`. For array (multimodal) content, edit and copy apply it to the first text part, as `backend/chat/message_edit.py` does. Copy uses the stripped text for user messages only (as `createMessageBubble` strips only user messages); other messages are copied as today. Edit shows the stripped text and records the note together with the chat it belongs to: `editNote = {chatId, note}` in `script.js` module scope, set through a new `deps.setEditNote` on every edit (`note` empty when the message has none). In `sendMessage`, only on the user-initiated path (after the `isGenerating` guard and the `/help` and `/skills` interceptors, and only when it is not a resume, reattach or approved-plan call), before Phase 0: `const note = editNote && editNote.chatId === currentChatId ? editNote.note : ""` is read and `editNote` is set to null; `const sentContent = content + note` (`content` is already trimmed; the note keeps its leading blank line, so a note-only send stores `\n\n[System Note: ...]`, which the display, edit and copy split cleanly) is then used wherever `content` built the user message (the chat title keeps using `content`). `loadChat`, `loadWorkspace` and `startNewChat` also set `editNote` to null. `sentContent` (not `content`) is what the empty-message check tests, so an edit sent with an empty textarea still sends the note as it does today (the textarea used to hold it), and Phase 0 runs exactly as now. Invariants: a note is appended only to the next user send in the same chat after an edit (that send is the edited message: in a saved chat Phase 0 replaces it, and in a temporary chat `editMessageAction` has already cut the local history at it, so whatever text it carries keeps the edited message's attachments; if that send fails, the note is not restored and a retyped resend goes without it, an accepted loss pinned by a test), with no chat change in between; internal sends (resume, reattach, approved plan) never consume or carry it; Phase 0 and the empty-message check behave as today. This mirrors `backend/chat/message_edit.py` (the note is re-appended to the edited text). Stored content is unchanged.

### Risks and open questions
- PDFs detected as spreadsheet or code keep whole-text chunking and can still report page 1 for later chunks (known limit; extractor text is almost always detected as document or mixed).
- Per-page chunking changes chunk boundaries for PDFs (no chunk spans a page break); retrieval quality is expected to be equal or better, but re-index results differ from today's.
- Re-indexing all files re-embeds everything (cost and time proportional to stored text) and needs the app stopped; `--file-id` allows a gradual run.
